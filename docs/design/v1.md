# V1 Design

## Status

Accepted on 2026-07-27.

## Purpose

DDD Lint is a standalone Rust-based Python linter. It detects structures that often hide domain states, weaken exhaustive behavior, or obscure dependency composition.

The linter enforces opinionated DDD proxies. A diagnostic means that a concrete syntax or type condition was found. It does not mean the linter proved the domain model wrong. Every rule documents its uncertainty and supports a narrow, reasoned design exception.

## Goals

- Give Python teams fast, deterministic checks for selected domain-modeling conventions.
- Make invalid or incomplete state handling visible through closed-type analysis.
- Scrutinize every supported, resolvable non-`RootModel` Pydantic `BaseModel` when a model rule is selected.
- Resolve first-party imports across normal projects and uv workspaces.
- Offer Ruff-like rule selection and concise diagnostics without depending on a Ruff plugin API.
- Keep all policy opt-in.

## Non-Goals

- Prove that a domain model is correct.
- Implement a complete Python type checker.
- Infer entities, value objects, aggregates, repositories, or domain layers from names.
- Modify source code in v1.
- Provide persistent caching, an editor server, notebook linting, or every Ruff output format.
- Support Pydantic 1, Python before 3.10, Pydantic dataclasses, or `RootModel` in v1.

## Compatibility

- Python source target: Python 3.10 or newer.
- Model framework: Pydantic 2.
- Parser: exact-pinned `ruff_python_parser` and `ruff_python_ast` crates.
- Rust toolchain: Rust 1.95 or newer, as required by the selected Ruff crates.
- Distribution: binary wheels on PyPI, built with maturin.

## CLI

V1 exposes three commands:

```text
ddd-lint check [PATHS...]
ddd-lint rule <CODE>
ddd-lint config
```

`check` emits human-readable text by default and supports JSON for machine integration. It never modifies Python files.

Exit codes follow this contract:

- `0`: analysis completed with no enabled violations.
- `1`: enabled violations, Python syntax errors, or invalid source suppression directives were found.
- `2`: invalid CLI/configuration or an internal failure prevented analysis.

## Configuration

DDD Lint reads one `pyproject.toml`. Outside a uv workspace, it searches upward from the invocation directory for the nearest file containing `[tool.ddd-lint]`. `--config` selects an explicit file.

No rules are enabled by default. Recommended onboarding configuration:

```toml
[tool.ddd-lint]
select = ["DM002", "CT", "DI001"]

[tool.ddd-lint.rules.DM002]
min-nullable-fields = 3
min-nullable-ratio = 0.30
```

Strict hardening adds the per-field model rules and suppression hygiene:

```toml
[tool.ddd-lint]
select = ["DM001", "DM002", "DM003", "CT", "DI001", "SUP001"]
```

Supported selectors are a full rule code, a family prefix, and `ALL`. `ignore` subtracts selectors from `select`. Unknown selectors are configuration errors. Family and `ALL` selectors intentionally opt into future rules added under that selector; exact codes pin policy more tightly.

Project defaults:

```toml
[tool.ddd-lint]
select = []
ignore = []
src = [".", "src"]
target-version = "py310"
```

Valid target versions are `py310`, `py311`, `py312`, `py313`, `py314`, and `py315`.

`src` paths are relative to the configuration root. File discovery respects `.gitignore`, `.ignore`, `.git/info/exclude`, and global Git ignore rules. It excludes `.git`, `.hg`, `.svn`, `.venv`, `venv`, `.tox`, `.nox`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `__pycache__`, `build`, `dist`, `site-packages`, and `node_modules` by default. Explicit input paths remain subject to ignore and `exclude` rules. Additional `exclude` patterns can narrow discovery further.

`exclude` and per-file patterns use glob syntax with `*`, `**`, `?`, and character classes. Paths are normalized to `/` separators and matched relative to the configuration root. Per-file `rules` entries accept full rule codes only, not family or `ALL` selectors.

`DM002` requires `min-nullable-fields` to be an integer of at least `1` and `min-nullable-ratio` to be greater than `0.0` and no greater than `1.0`.

### Per-File Design Exceptions

Configuration-level exceptions require structured reasons:

```toml
[[tool.ddd-lint.per-file-ignores]]
pattern = "tests/fixtures/**"
rules = ["DM001", "DM003"]
reason = "Fixtures intentionally represent malformed external payloads"
```

`exclude` means a path is outside analysis. `per-file-ignores` means analyzed code contains accepted violations. Only the latter requires a design reason.

## uv Workspaces

When `[tool.uv.workspace]` is present, DDD Lint treats that `pyproject.toml` as the workspace root:

- `[tool.ddd-lint]` at the workspace root defines one policy.
- `tool.uv.workspace.members` and `tool.uv.workspace.exclude` determine member projects.
- The root and each included member contribute `.` and `src` import roots.
- All members form one symbol graph, allowing cross-member type resolution.
- Paths passed to `check` limit emitted diagnostics, not the files required for type indexing.
- Member-level `[tool.ddd-lint]` tables are unsupported in v1.
- Duplicate importable module names across roots are configuration errors.

DDD Lint reads workspace metadata directly; it does not invoke `uv`.

## Analysis Pipeline

Each `check` performs a deterministic two-pass project analysis:

1. Discover `.py` and `.pyi` files from project and workspace roots.
2. Parse files in parallel through the internal Ruff adapter.
3. Index modules, imports, aliases, classes, fields, functions, parameters, and return annotations.
4. Resolve first-party symbol relationships and supported type forms.
5. Run enabled rules against `.py` files.
6. Parse and apply source and configuration design exceptions.
7. Sort diagnostics by path, source offset, and rule code.
8. Render text or JSON and choose the exit code.

`.pyi` files contribute declarations to the index but never produce DDD Lint rule or suppression diagnostics. A `.pyi` syntax error still produces a source error because the project graph cannot index that declaration reliably.

V1 has no persistent cache. The parser and indexing passes may execute in parallel, but output ordering remains stable.

## Type Resolution Boundary

DDD Lint performs declared type flow, not full inference. It resolves:

- annotated parameters and names;
- PEP 604 unions and `typing.Union`;
- `Literal`, `Annotated`, and project-local aliases;
- quoted annotations and postponed annotations;
- known attributes on resolved first-party classes;
- simple name-to-name assignments;
- calls to resolved functions with annotated returns;
- direct and indirect project-local inheritance;
- standard aliased imports such as `import pydantic as p` and `from pydantic import BaseModel as Model`.

DDD Lint skips a diagnostic when required type facts cannot be proven. It does not guess through wildcard imports, dynamic class creation, monkey-patching, unresolved third-party declarations, or general data flow.

## Pydantic Model Semantics

Model rules inspect direct or project-resolvable indirect subclasses of Pydantic 2 `BaseModel`, excluding `RootModel` and every `RootModel` descendant.

- Only fields declared in the current class body contribute diagnostics and counts.
- Inherited fields are checked at their declaring class, preventing repeated subclass findings.
- A field is nullable only when its resolved top-level type admits `None`, such as `T | None`. Nested `None` in `list[T | None]`, `Callable[..., None]`, or another contained type does not make the field nullable.
- `Any` and `object` are not treated as explicitly nullable.
- A field is defaulted when any assigned expression supplies its value or when `Field` metadata supplies `default` or `default_factory`, including inside `Annotated`.
- Required `Field(...)`, `Field` metadata without a default, and other metadata-only declarations are not defaults.
- `ClassVar`, private attributes, and computed fields are not model fields.

## Closed Types

V1 recognizes these finite domains:

- an explicit union whose non-`None` alternatives are all resolvable classes and which contains at least two such classes;
- `Literal` alternatives supported by Python match patterns;
- project-resolvable `Enum`, `StrEnum`, and `IntEnum` members.

`T | None` alone is excluded to avoid turning every absence check into required pattern matching. If an otherwise eligible union includes `None`, `None` is a required explicit case.

`Flag` and `IntFlag` are excluded because values can combine declared members. Enum aliases collapse to their first canonical member.

Class-union members must be pairwise non-overlapping in the known project hierarchy. If one member is a known base of another, DDD Lint skips closed-type diagnostics for that union. Literal members must also be distinguishable by Python pattern semantics; alternatives that are distinct to typing but equal at runtime, such as `1` and `True`, make the type ineligible. These restrictions avoid claiming exhaustiveness when one pattern can consume another member.

## Match Semantics

When `CT001` is enabled, an exhaustive match must explicitly cover every closed member:

- Class unions use member class patterns such as `case Draft():`.
- Literal types use literal patterns.
- Enums use member value patterns such as `case Status.OPEN:`.
- OR patterns and `as` wrappers contribute all explicit members they contain.
- A guarded case never provides complete coverage for its member; an unguarded case must also cover it.
- Capture, wildcard, base-class, mapping, and sequence patterns do not stand in for explicit members.
- A wildcard never contributes member coverage to `CT001`.

When `CT002` is enabled, `case _` is rejected for a closed type, including after complete explicit coverage. When `CT004` is enabled, matching a recognized class union through its discriminator attribute is rejected. Class patterns preserve the modeled alternatives. Adding a member creates missing-coverage diagnostics at match sites when `CT001` is enabled.

## Conditional Dispatch

`CT003` rejects direct member selection in `if`, `elif`, and ternary expressions. V1 recognizes:

- `isinstance(value, Member)`;
- `type(value) is Member`;
- equality and identity comparisons against enum or literal members;
- equality against a common discriminator field whose class-union members declare distinct singleton `Literal` tags;
- negated forms and reversed comparison operands.

Loops, comprehensions, assertions, and match guards are outside `CT003`. General boolean/set solving, helper predicates, and membership tests are deferred.

## Suppression Directives

DDD Lint uses its own namespace to avoid conflicts with Ruff's `noqa` validation.

Inline design exception:

```python
email: str | None  # ddd-lint: ignore[DM001] - Absence is domain-significant
```

Declaration design exception:

```python
# ddd-lint: ignore[CT003] - Adapter mirrors a third-party branching protocol
def dispatch_external_message(message: Message) -> None:
    ...
```

A directive immediately above a function or class covers that declaration's subtree. Above another statement, it covers that logical statement. A trailing directive covers its physical source line.

The source grammar is case-sensitive:

```text
# ddd-lint: ignore[DM001, DM003] - non-empty reason
# ddd-lint: file-ignore[DM001, DM003] - non-empty reason
```

Codes are uppercase full rule codes separated by commas. Family selectors and `ALL` are invalid in source directives. The ` - ` delimiter and non-empty text after it are mandatory.

An own-line `ignore` attaches to the next logical statement only when no blank line or unrelated comment intervenes. Consecutive DDD Lint directives may be stacked. For a decorated function or class, the directive must appear immediately before the first decorator. A directive before the first line of a multiline statement covers the entire statement; a directive inside that statement or trailing one of its lines covers only that physical line.

File design exception:

```python
# ddd-lint: file-ignore[DM001, DM003] - Legacy wire schema mirrors partner API
```

File directives must be own-line comments before the first Python statement. A shebang and encoding comment may precede them. Every directive requires at least one explicit rule code and non-empty reason text. Blanket ignores do not exist.

Malformed directives, unknown codes, missing reasons, and invalid placement always produce source errors. `SUP001` optionally evaluates each code listed by a source directive or configuration per-file entry and reports a code that suppresses no enabled diagnostic in that scope. Every code in a per-file entry whose pattern matches no analyzed file is unused. Source directives report at the comment; configuration findings report at the relevant TOML entry.

`SUP001` cannot be listed in a source directive or `per-file-ignores`; either use of the code is an invalid suppression. This prevents a suppression from proving its own use. Disable `SUP001` through the project-level `ignore` selector when suppression hygiene is intentionally not enforced.

## Diagnostics

Every selected rule has equal failing status; v1 has no warning/error severity levels. A diagnostic contains:

- stable code and rule name;
- path and precise source range;
- concise observed condition;
- remediation direction;
- rule documentation reference;
- machine-readable fields in JSON output.

Project-level type uncertainty never produces a lower-confidence diagnostic. The analyzer either establishes the rule's required facts or skips it.

## Deferred Work

- Role markers for entities, value objects, aggregate roots, repositories, and domain modules.
- Import-boundary and aggregate-reference rules.
- Persistent incremental cache and editor integration.
- Additional Python type inference.
- Pydantic dataclasses and `RootModel`.
- Jupyter notebooks and additional output formats.
- Safe or unsafe fixes.
